# 安全模型

RunLoft 会启动来自 Git 仓库的程序，并在本机显示其 Web 页面。仓库代码和配置都应视为不可信输入，直到用户完成审查。下载公开仓库不代表用户已经授权执行其代码。

## 1. 信任与命令执行

- clone/fetch 与执行命令是不同操作；第一次 prepare/start 前展示将运行的命令、参数、工作目录和重要环境变量。
- 授权应绑定仓库、配置摘要和命令；配置变化后再次确认。
- 使用参数数组直接启动进程，不默认经由 shell；不支持隐式管道、重定向或命令替换。
- 工作目录限制在仓库内；不把仓库路径、配置字段直接拼进 shell 命令。
- `prepare` 步骤只能由用户主动触发；不得因 clone 或启动应用而静默执行。整组步骤须按序运行，失败后停止且不自动重试。
- MVP 不自动安装或更新 Node.js 等运行时；目标项目依赖仍通过经用户审查授权的准备步骤处理。
- 日志需对令牌、口令和已知敏感环境变量做遮盖；避免将完整进程环境写入日志。

## 2. Git 和本地数据保护

- 仅在用户主动检查更新时执行 fetch；只有用户明确确认后才应用快进更新。
- 更新前检查工作区状态；有未提交改动、未跟踪文件或分支分叉时阻止更新。
- 不使用会丢弃用户工作的 reset/clean 操作，也不自动 stash/pop。
- 用户明确移除项目时说明代码工作区和 RunLoft 元数据的影响；默认不递归删除工作区。
- 凭据委托给系统 Git credential helper 或 SSH agent；MVP 不在 RunLoft 数据库中保存访问令牌。

## 3. WebView 与本地服务

- 默认只加载绑定到 loopback 地址的项目服务。
- 校验 scheme、host、端口和重定向目标；拦截导航到远程站点、`file:` 和其他本地服务。
- 将外部链接交给系统浏览器；目标项目页面不获得 RunLoft 的 Go 绑定或特权 IPC。
- 每个项目单独管理 WebView 数据目录或清除策略，避免在不同项目之间意外共享登录状态。
- MVP 不承诺抵御已授权目标项目本身的恶意行为；用户授权后启动的程序仍可使用当前用户权限访问本机资源。

## 4. 进程和端口

- 服务应绑定 `127.0.0.1`，除非用户显式修改并确认配置。
- RunLoft 只终止自己创建的进程及其子进程，不按端口号查杀其他程序。
- 端口冲突时不得把 WebView 导航到占用端口的其他服务；停止启动流程并提示处理。
- 关闭应用时先优雅停止项目进程，随后在限定超时内清理进程组，并记录无法停止的情况。

## 5. 需要验证的边界

- MyGo 页面导航回调在首发平台上是否足以实施上述 URL 策略。
- WebView 对 loopback 服务的 cookie、跨源请求、WebSocket 和隔离 profile 行为。
- macOS、Windows、Linux 上进程组创建和结束方式是否存在差异。
- Git hooks、过滤器和仓库内容在克隆及更新路径中的执行边界；相关 Git 参数应在实现时逐项审查。

## 6. 安全验收

- 未经授权的命令不能启动；修改命令后旧授权失效。
- 目录穿越配置被拒绝。
- 非 loopback URL、恶意重定向和外链按预期拦截。
- 本地有改动时更新不会改变工作区内容。
- 停止一个项目不会终止其他项目或用户手工启动的进程。
- 日志中不出现配置的秘密值或完整环境转储。
